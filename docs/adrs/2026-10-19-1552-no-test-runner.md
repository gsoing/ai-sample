## Date

## Context

`aidlc-docs/aidlc-state.md` declares the `dso-foundation` governance opt-in. Four Foundation rules assume that the project has automated tests:

- `DEV-TEST-BP01-R01` (MUST, scope "All projects"): unit, integration and end-to-end testing layers
- `DEV-TEST-BP01-R02` (MUST, scope "All projects"): tests run automatically on every commit via pre-commit hooks and CI/CD
- `DEV-CODE-BP02-R01` (MUST, scope "All languages, new code only"): minimum 80% test coverage on new code
- `DEV-CODE-BP02-R02` (MUST, scope "All projects"): code passes automated quality gates before merging

This project has no test runner. `AGENTS.md` states it ("No test runner is configured yet"), and the training it supports is built around that fact: the quality gates are `pnpm lint`, `pnpm typecheck` and `pnpm build`, run by the developer and by the `reviewer` sub-agent. Adding a runner is an optional extension of the training, not a prerequisite.

Claiming compliance with the four rules above would be dishonest, since no test exists. The `dso-foundation` opt-in forbids it: a `[MUST]` acceptance criterion that cannot be honestly satisfied is downgraded to `[SHOULD]` and justified by an ADR.

## Decision

**This project has no test runner. The four rules above are downgraded from `[MUST]` to `[SHOULD]` once, here, for the whole backlog.**

| Rule | Status here | AC severity in stories |
|---|---|---|
| `DEV-TEST-BP01-R01`: test layers | Not satisfied, no test exists | `[SHOULD]` |
| `DEV-TEST-BP01-R02`: tests on every commit | Not satisfied, no test and no CI | `[SHOULD]` |
| `DEV-CODE-BP02-R01`: 80% coverage on new code | Not satisfied, coverage is not measured | `[SHOULD]` |
| `DEV-CODE-BP02-R02`: automated quality gates before merge | Partially: `lint`, `typecheck` and `build` run locally, nothing blocks a merge | `[SHOULD]` |

What replaces tests in a story:

- Acceptance criteria are written as Given/When/Then and verified by hand, with `curl` for the API and the browser for the web app.
- `pnpm lint`, `pnpm typecheck` and `pnpm build` must pass before a story is declared done.

Individual stories must not restate this downgrade. They link this ADR in `related_adrs` and reference it from the affected criterion.

This is a **"won't do for this project", not a "not yet"**. No story to add a runner should be created without superseding this ADR.

## Alternatives Considered

### Alternative 1: Add vitest and write tests for the existing code

- **Evaluation**: Would satisfy `DEV-TEST-BP01-R01` and `DEV-CODE-BP02-R01`, and give the reviewer a stronger signal than reading code.
- **Rejection rationale**: Out of the training's scope. Test-driven agent workflows are a separate topic, and a runner would add a dependency and a new gate to every lab. Kept as an optional extension.

### Alternative 2: Claim compliance and keep the acceptance criteria at `[MUST]`

- **Evaluation**: Zero effort. The backlog would look fully Foundation-compliant.
- **Rejection rationale**: Dishonest and explicitly forbidden by the `dso-foundation` honesty rule. Every story would also carry a criterion that nobody can verify.

### Alternative 3: Downgrade the rules story by story

- **Evaluation**: Keeps each story self-contained.
- **Rejection rationale**: Repeats the same justification in every story and invites each one to decide differently. One ADR decides it once.

## Consequences

### Positive

- The severity of every test-related criterion is unambiguous and one link away.
- The compliance claim of the project stays true.
- The lab flow stays short: no runner to install or explain.

### Negative

- **Nothing verifies behaviour automatically.** A regression is caught only if someone checks by hand or the reviewer spots it.
- **No coverage figure** exists, so quality cannot be trended.
- **Rules about CI are not covered here.** The project has no CI either (`ci.claude_code_action: false`). Rules such as `DEV-BUILD-BP03` are not addressed by this ADR and remain open if the project leaves the training context.
- Moving this project toward production requires superseding this ADR first.

### Trade-offs

- Training focus over enforcement: the project exists to teach the workflow.
- An honest `[SHOULD]` over a fake `[MUST]`: the project looks less compliant on paper, but the claim survives an audit.

## Security Implications

Required per `DEV-CODE-BP01-R03`.

- **Weakened control:** the absence of tests means no automated check of input validation or error handling. A validation regression in an API route can reach `main` unnoticed. Mitigation: the reviewer sub-agent and the manual Given/When/Then checks cover the changed behaviour.
- **New attack surface:** none. Not adding a test toolchain adds no dependency.
- **Data classification:** no impact. The quotes are fictional training data.
- **Top risk:** a silent regression in validation. Accepted for a training project with no production deployment.
